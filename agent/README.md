# CraftLab Agent 工程规划

`agent/` 是一个可由 CLI 和后端共同调用的 Node.js 24 + TypeScript 包。首个场景是学习产物评审。Agent 接收验收条件、产物和可用工具，决定本轮该看什么、还缺什么证据，以及何时可以给出结论。[产物评审场景](../docs/articles/01-what-is-agent.md)

## 工程边界

| 工程 | 负责的决定 |
| --- | --- |
| `agent/` | 给模型哪些指令和上下文，允许它选择哪些工具，如何核实工具结果和模型结论，何时补证、压缩上下文或停止。返回逐项结论、证据引用和结束原因。 |
| `backend/` | 谁可以评审哪份提交，适用哪个版本的验收规则，本次授权覆盖哪些产物。保存报告，并决定是否进入返工或解锁下一项任务。 |
| `demos/` | 用独立小程序演示单项机制。Agent 包将上下文组装、压缩、工具调用、结构化输出等机制用于同一次任务。 |

依赖方向为 `backend → agent`。拟定公共入口为 `reviewSubmission(input, { model, tools, limits })`。调用方传入验收规则和授权后的工具，Agent 按规则计算并返回结果。CLI 从本地读取输入，后端从业务记录构造输入，两者使用同一入口。

## 目录划分

以下为规划。当前工程仅有本文。

```text
agent/
├── README.md
├── package.json             # ESM 导出、类型声明、构建与测试脚本
├── tsconfig.json
├── src/
│   ├── index.ts             # 提供给 CLI 和 backend 的公共接口
│   ├── cli.ts               # 本地运行一次评审并打印结果
│   ├── review/              # 学习产物评审用例、验收项、报告契约
│   ├── prompts/             # 评审、摘要、语义核验的指令模板与版本
│   ├── context/             # 选择资料、估算 token、组装消息、压缩历史
│   ├── runtime/             # 执行循环、单次运行状态、步数与取消控制
│   ├── models/              # 模型适配、结构化输出解析、实际用量
│   ├── tools/               # 工具声明、参数检查、在授权范围内执行
│   ├── verification/        # 核对证据来源、覆盖范围、冲突和结论
│   └── scoring/             # 将已核验结果换算为指标，执行验收阈值规则
├── test/                    # 确定性测试，含工具结果、模型响应等固定样本
└── evals/                   # 带人工预期结论的案例，比较提示词或模型版本
```

## 一次评审中的能力分工

以“待办应用刷新后仍保留数据”为例。假设工具返回两条通过的测试，一条测新增待办，一条测切换状态。Agent 需要判断这两条结果究竟能证明什么。

| 模块 | 输入、动作与输出 |
| --- | --- |
| 提示词 | `prompts/` 定义评审目标、证据引用格式和资料不足时的回答方式。评审、生成历史摘要、核验摘要分别使用对应的模板；运行记录保留实际使用的模板版本。 |
| 上下文 | `context/` 每轮选入当前验收项、工具定义、相关证据和未解决的问题。工具输出保留来源标识，作为资料传给模型。历史过长时压缩旧轮次，保留最新更正与证据引用，核对摘要后再替换请求中的历史。[组装示例](../demos/04-context-assembly/index.mjs) · [压缩示例](../demos/07-context-compaction/index.mjs) |
| 执行循环 | `runtime/` 持有本次任务的原始证据和剩余预算，调用模型取得工具请求，交给已授权的工具执行，再将结果送入下一轮。模型可据此请求运行刷新测试，或指出还缺哪项材料。 |
| 验真 | `verification/` 将结论绑定到本次提交的文件版本、测试用例和实际输出。先检查引用是否存在、用例是否覆盖目标行为，再根据测试断言和输出核对结论。需要语义判断时输入原文与候选结论；遇到相互冲突的证据，保留双方引用并请求补证。示例中的两条测试都通过，但刷新行为仍为“待验证”。 |
| 评分与阈值 | `scoring/` 接收逐项的“通过、失败、待验证”和对应证据，按任务提供的必选项、分母和边界计算结果。输出原始计数、计算值和命中的规则，便于复核。 |
| 输出与回归 | `review/` 汇总报告。后端根据报告推进任务。修改模板、上下文策略或阈值后，用 `evals/` 的固定案例检查误判，尤其关注“证据不足却判为通过”的样本。 |

## 阈值如何计算

阈值由使用它的模块维护。下面的规则用于说明首版行为，业务验收门槛随任务传入。

| 决策点 | 计算与边界 | 所属模块 |
| --- | --- | --- |
| 本轮输入能否放进模型窗口 | 可用输入预算 = 模型窗口 − 预留输出 − 安全余量。对包含指令、消息和工具定义的完整请求估算 token；超出预算时压缩历史并重新估算。若必需内容仍放不下，返回上下文超限原因。 | `context/` |
| 能否开始下一轮 | 每次准备发起模型调用前，检查已用步数和剩余预算。已用步数达到上限时停止，并返回已有证据与未验证项。 | `runtime/` |
| 证据覆盖了多少验收项 | 已核验覆盖率 =（有证据支持通过的项数 + 有证据支持失败的项数）÷ 适用项总数。每个验收项只计一次；分母为零时返回“不适用”。 | `verification/` 提供逐项状态，`scoring/` 计算 |
| 是否达到验收门槛 | 例如任务要求三项必选行为全部通过，前两项通过、刷新待验证时，覆盖率为 2/3，总体待验证。补测刷新且复现丢失后，覆盖率为 3/3，总体失败。有已证实的必选项失败即判失败。 | `scoring/` |

## 首版如何验证

- 用同一份任务分别从 CLI 和包入口调用，固定模型响应和工具结果，检查两条路径返回相同的逐项结论与证据。
- 将旧记录中的“刷新成功”更正为“刷新后丢失”，触发历史压缩，检查下一轮仍引用最新记录。若摘要丢失更正，舍弃候选摘要并重新处理上下文。
- 让模型提交一个格式正确但引用无关测试的报告，检查验真环节能定位缺口。切换到实际覆盖刷新的测试后，检查结论随执行证据变化。
- 覆盖输入预算刚好用满、超出预算、步数耗尽、验收项为空，以及必选项失败等边界。固定样例用于测试规则，人工标注样本用于比较模型与提示词版本的判断质量。
